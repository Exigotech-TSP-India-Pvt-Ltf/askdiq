    Guide · human feedback loop

    How feedback works

    People rate the assistant's answers. Admins review the bad ones, then turn them into three things: regression tests (golden cases), training data (preference pairs), and a list of missing documents (knowledge gaps). AskDIQ does not retrain any model itself. It collects and exports the data.

    The loop, one step at a time

    Click a step, or use Back and Next. Each step says what happens in plain words, then what the code does.

    1 · The user clicks thumbs up or thumbs down

    Every assistant answer in the chat, and in the dashboard widget, has two buttons. Thumbs up stores a rating of 5. Thumbs down stores 1 and opens a small panel: What went wrong? with reason chips, plus an optional box What should it have said?. After rating, the user can also add a short note.

    👍 Helpful = 5👎 Unhelpful = 1

    The database accepts 1 to 5, and the admin pages show stars, but the chat only ever sends 1 or 5. Ratings of 2 to 4 only come from other clients or seeded data.

    In the code
    Reason chips: Wrong Incomplete Off topic Unsafe Too slow Unclear
    Request: POST /sessions/{sid}/messages/{mid}/feedback with rating, comment (≤ 1000 chars), reason_tags, corrected_answer (≤ 4000 chars). Rate limit 30 per minute.
    Source: frontend/components/MessageBubble.tsx (THUMBS_UP = 5, THUMBS_DOWN = 1), frontend/components/chat/FeedbackReasonPanel.tsx, frontend/lib/feedback-api.ts, backend/app/api/routes/sessions.py, backend/app/schemas/session.py

    2 · One row per answer and person

    The rating is saved in message_feedback, linked to the exact assistant message and its conversation. If the same person rates the same answer again, the row is updated, not duplicated. The comment and the suggested answer are PII-masked before they are stored.

    The sources are not copied onto the rating. When an admin opens it, the page joins the sources the answer actually used (from that answer's evaluation record), so the reviewer sees the question, the answer and the cited passages side by side.

    Right after saving, a check counts the last hour of ratings. More than 25% negative (with at least 5 ratings) writes a negative_feedback_spike audit event.

    3 · It shows up as New in the Review Queue

    Every rating starts with the triage status New. The Review Queue shows New items by default, newest first, 25 per page, with filters for status, rating, outcome, grounded and comment. Click a row (or press Enter) to open the drawer: question, answer, labels and flags, sources, the user's feedback, a box for the correct answer and a reviewer note.

    The queue is keyboard-first: j/k move, Enter opens, x selects, r reviewed, d dismiss, p promote.

    Triage statuses
    newreviewedpromoteddismissed
    Viewing needs dashboard:read; acting needs feedback:triage (admin, superadmin). Operators see the queue read-only.
    Source: backend/app/schemas/feedback.py (TriageStatus), frontend/components/admin/feedback/ReviewQueue.tsx, FeedbackDrawer.tsx, backend/app/api/routes/admin_feedback.py (GET /admin/feedback)

    4 · The admin picks one action

    • Dismiss (d): noise, or the answer was fine. It can be undone (back to New).
    • Mark reviewed (r): a real problem you handled, for example by fixing a document. Add a note saying what you fixed. There is no separate "mark fixed" status; reviewed plus a note is how it is recorded.
    • Promote to test (p): turn the question into a golden case so it is re-tested later. Final: a promoted rating cannot change again.
    • Write the correct answer in the drawer: it becomes the "chosen" side of a preference pair and the golden case's reference answer.
    • Add document (Knowledge Gaps tab): for questions the knowledge base does not cover. It opens the Documents page, where you upload the file.
    Allowed moves (enforced on the server)
    new→ reviewed, promoted, dismissed
    reviewed→ promoted, dismissed
    dismissed→ new (restore)
    promotedfinal, no moves
    A forbidden move returns 409. Bulk actions take up to 200 rows, all or nothing. Promoting a message also flips every other open rating of it to promoted.
    Source: backend/app/feedback/service.py (TRANSITIONS, _promote_message), backend/app/feedback/repository.py (mark_message_promoted), frontend/components/admin/feedback/triage.ts, KnowledgeGapsTab.tsx (ADD_DOCUMENT_HREF)

    5 · Four outputs

    • Golden set: promoted questions stored in eval_promoted_cases, re-run on demand.
    • Preference pairs: a JSONL download, one line per rating, with a prompt, a chosen (better) answer and a rejected (worse) answer. Ready for a later fine-tuning run (DPO or SFT) outside AskDIQ.
    • Knowledge-gap list: questions with low ratings and weak retrieval, grouped, top 10.
    • Alerts: the Negative feedback spike alert in the notification bell and by email.
    How a pair is built
    has corrected answerchosen = corrected, rejected = bot answer → complete
    rating 4–5, no correctionchosen = bot answer, rejected = missing
    rating 1–3, no correctionchosen = missing, rejected = bot answer
    Line keys: feedback_id, message_id, prompt, chosen, rejected, rating, reason_tags, source_ids, triage_status, created_at, complete, missing. Dismissed ratings are left out by default. Needs feedback:export.
    Source: backend/app/feedback/service.py (build_pair), backend/app/api/routes/admin_feedback.py (GET /admin/feedback/export, /pairs), backend/app/feedback/analytics.py (_knowledge_gaps)

    6 · Golden cases are tested again

    On the Golden Cases tab, Run now queues a background job that sends the stored question through the real answer pipeline again. The chip next to the button goes Queued → Running… → Passed or Failed.

    The offline evaluation script also adds every golden case to its test set on each run. See How evaluation works.

    What "Passed" means today: the new answer's groundedness matches what was promoted, and there was no error. The stored correct answer is not compared with the new answer.
    In the code
    POST /admin/feedback/golden/{case_id}/run (202) enqueues job eval.golden_run, deduplicated per case (a second click says "Already queued"). Results land on the case: last_run_at, last_run_passed, last_run_detail.
    The UI polls every 3 s, up to 40 times, then shows "Still running".
    Source: backend/app/api/routes/admin_feedback.py (run golden case), backend/app/jobs/handlers.py, backend/app/evaluation/evaluator.py, frontend/components/admin/feedback/GoldenCasesTab.tsx (GOLDEN_POLL_MS = 3000, GOLDEN_MAX_POLLS = 40)

    Worked example: one bad answer, end to end example

    Made-up text to show the mechanics. The steps, statuses and fields are real.

    example How long do you keep backup snapshots for managed servers?
    example Backup snapshots are kept for 7 days.
    👎 rating 1reason: wrongreason: incomplete
    What should it have said? example Daily snapshots are kept for 30 days and monthly ones for 12 months.
    1. Stored. A message_feedback row: rating 1, reason_tags ["wrong","incomplete"], corrected_answer (PII-masked), triage_status new.
    2. Reviewed in the queue. The admin opens the drawer and sees the answer cited an older backup document with a low score.
    3. Fix the source. The admin uploads the current backup policy on the Documents page (the gap fix).
    4. Promote to test. A golden case promoted_<message id> is created with the question, the corrected answer as reference, and the expectation taken from the old answer (grounded or not).
    5. Run now. The case is re-asked through the pipeline; the chip shows Passed or Failed.
    6. Export. The JSONL now has a complete line: prompt = the question, chosen = the corrected answer, rejected = "kept for 7 days".
    Source: backend/app/feedback/service.py (_promote_message, build_pair), backend/app/models/db_models.py (MessageFeedback, EvalPromotedCase)

    Guide · answer quality

    How evaluation works

    Evaluation means grading the assistant's answers, either on a fixed set of test questions (offline) or on real answers as they happen (online). Some grades are simple rules computed by code; some come from an AI "judge" that reads the answer and the sources. This page lists exactly which is which.

    Golden setOffline vs onlineWhere it hooks inEvery metricScore readerHow to run itRead with care

    What a golden set is

    A golden set is a list of test questions with the behaviour we expect. Re-running it after any change (a new prompt, model, document or setting) shows whether something that used to work broke. That is regression testing.

    Offline vs online evaluation

    Offline asks the golden-set questions through the real pipeline on demand, then checks each answer against its expectations: the right document retrieved, keywords present, grounded as expected, safe, and (with --judge) a judge faithfulness of at least 4. It has right answers to compare with, so it can measure ranking quality (Recall@k, MRR, nDCG). Run by the script, or one case at a time with Run now.
    Online grades real answers right after they are sent, in the background, so users never wait for it. There is no right answer to compare with, so it uses rules (groundedness, word overlap with the sources, PII and secret scans) on every answer, and the AI judge on a 10% sample when it is switched on. Results go to evaluation_records and the Evaluation page's Users audience.

    How to run an evaluation

    A · One golden case, from the console
    1. Open Feedback › Golden Cases.
    2. Click Run now on a case (needs feedback:triage). The job chip shows Queued → Running… → Passed / Failed.
    3. The result stays in the Last evaluation column (passed, confidence, error). It is not shown on the Evaluation page.
    Source: frontend/components/admin/feedback/GoldenCasesTab.tsx, backend/app/feedback/jobs.py (eval.golden_run)
    B · The full benchmark, from the server

    From backend/ with the venv:

    .venv/bin/python scripts/run_evaluation.py --judge --json reports/eval_report.json

    Useful options: --ids, --types, --min-pass-rate (exit code 1 below it, for CI), --repeat (robustness), --top-k (default 6), --judge-min-faithfulness (default 4), --kb / --kb-only (knowledge-base checks), --price-in / --price-out. Golden cases from the database are merged in automatically. There is no API or button for the full run.

    Source: backend/scripts/run_evaluation.py
    C · Read the results on the Evaluation page
    1. Sidebar Evaluation (/admin/evaluation-live). The audience picks the data: Overview and Testing show the newest benchmark report file; Users shows live evaluation_records.
    2. Quality & Retrieval tab: tiles, the radar, and Pass-rate trend, one marker per run (a report file, or one UTC day of live records; latest 30).
    3. Compare with benchmark (header button): live vs benchmark for pass rate, faithfulness, retrieval recall and citation precision, plus a dual radar.
    4. Query & Case Explorer tab: filter Failed Only, then Inspect a row to open the case drawer: Interaction & Audit, LLM Judge Breakdown, Sources & Citations, Latency & Ops.

    Read with care: what the code does not do (yet)

    • The AI judge is off by default (ONLINE_EVAL_ENABLED=false). Live faithfulness, relevance and completeness are then a formula (for example faithfulness = 3.8 + 1.2 × citation precision when grounded), even on tiles labelled "LLM Judge".
    • Live retrieval recall is not a real recall: 1.0 whenever sources were found and the answer was not ungrounded.
    • Golden-case "Passed" checks only groundedness and errors; the reference answer is not compared.
    • Benchmark defaults: when a report file lacks a per-case value, the page fills faithfulness 4.8, relevance 4.9, citation precision 0.94, recall 0.98 and similar, so an unjudged report looks judged.
    • Static text in Compare: the "Model Drift & Alignment Assessment" figures are hardcoded, and its note about alerts below faithfulness 3.5 or safety 98% has no matching rule. The real alert fires on 3 or more online-eval violations in 60 minutes.
    • Prompt-injection in the live safety score looks for a flag (injection_detected) no guardrail emits; blocked injections are flagged unsafe_input_detected and stopped before an answer exists.
    • Permission eval:run exists but no route checks it; Run now uses feedback:triage.

    Guide · Azure Insights (PR #62)

    Microsoft Azure: what we call and what we get

    Besides chat and embeddings, AskDIQ can read facts about its own Azure OpenAI resource from Microsoft: official prices, Azure's own token and request counts, the bill, real rate limits, health and Advisor notices. It is off by default, read-only, and uses free APIs. Background jobs fetch the data on a schedule and store it in Postgres. Console pages read only what is stored.

      How to switch it on

      1. Create a separate Entra app registration (not the sign-in one, ENTRA_*) and give it only read roles, listed below.
      2. On the server set AZURE_INSIGHTS_ENABLED=true and the ids: AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET, AZURE_SUBSCRIPTION_ID, AZURE_RESOURCE_GROUP, AZURE_OPENAI_RESOURCE_NAME, AZURE_OPENAI_REGION. If one is missing or malformed, the API refuses to start with a message naming it.
      3. Optional: AZURE_SERVICE_HEALTH_ENABLED=true and AZURE_ADVISOR_ENABLED=true (these need subscription-scope read), and AZURE_MONTHLY_BUDGET for the billed-budget alert.
      4. Restart. The first polls run at once; the Azure connection card on Governance › Monitoring shows each source's state.
